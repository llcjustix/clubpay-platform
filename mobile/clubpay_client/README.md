# ClubPay Client

Нативный Flutter-клиент профиля игрока. Экраны построены на Flutter widgets;
WebView отсутствует. Платёжные страницы открываются через `url_launcher`
во внешнем браузере. Игровое время хранится в секундах отдельно по клубам.
Денежного кошелька в приложении нет.

## Запуск в Chrome

Для первого входа без настроенного Telegram-бота используйте
[локальный OTP-стенд и пошаговый сценарий](docs/FIRST_LOGIN_TEST.md).
Обычный API без `TELEGRAM_BOT_TOKEN` вернёт `503 telegram_unavailable`;
одного запуска Flutter недостаточно для входа.

Проверено с Flutter **3.44.6**, Dart **3.12.2**. Xcode не требуется.
Из корня репозитория:

```sh
cd mobile/clubpay_client
flutter pub get
flutter gen-l10n
flutter run -d chrome --web-port=7357 \
  --dart-define=API_BASE_URL=http://localhost:8088
```

`API_BASE_URL` задаётся при сборке и указывает только на публичный ClubPay API.
Без параметра используется `https://api-clubpay.justix.uz`; новые API необходимо
сначала развернуть. QR никогда не становится адресом HTTP-запроса: приложение
извлекает из ссылки только token и проверяет его на настроенном API.
Для веб-хранилища используйте HTTPS либо localhost.

Локальный backend запускается из корня репозитория, с отдельной БД:

```sh
DATABASE_URL='postgres://USER@127.0.0.1:5432/clubpay_mobile_dev?sslmode=disable' \
HTTP_ADDR=127.0.0.1:8088 \
PUBLIC_BASE_URL=http://localhost:8088 \
MOBILE_RETURN_BASE_URL=http://localhost:7357 \
TELEGRAM_POLLING_ENABLED=false \
go run ./cmd/api
```

Backend применяет SQL-миграции при старте. Не используйте production БД для
локальных испытаний: существующие миграции платформы содержат demo seed.

Для настоящего входа нужен настроенный `TELEGRAM_BOT_TOKEN` и имя бота
`TELEGRAM_BOT_USERNAME` (либо доступ к Telegram getMe). Доставка updates:

- polling: `TELEGRAM_POLLING_ENABLED=true`, без одновременного webhook;
- webhook: `TELEGRAM_WEBHOOK_SECRET`, установленный также через Telegram
  `setWebhook(secret_token=...)`. Мобильная авторизация **не принимает**
  неаутентифицированные webhook updates; старый QR flow сохранён.

Секреты задаются в окружении backend, никогда в Dart или `--dart-define`.
Без Telegram-конфигурации приложение показывает локализованное сообщение
о недоступности входа; тестовый профиль автоматически не подставляется.

## Проверки

```sh
# Из mobile/clubpay_client
flutter gen-l10n
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
flutter test --platform chrome
flutter build web

# Из корня репозитория
MOBILE_TEST_DATABASE_URL='postgres://USER@127.0.0.1:5432/clubpay_mobile_test?sslmode=disable' \
  go test -race ./...
```

Go integration test создаёт и удаляет **собственную схему** в указанной тестовой
БД. Без `MOBILE_TEST_DATABASE_URL` интеграционный тест явно пропускается.
Telegram HTTP перехватывается тестовым транспортом: сообщения реальным людям
и реальные платежи не отправляются. Flutter flow tests используют только
тестовый Dio adapter, не production API.

## Устройство проекта

- `lib/core`: HTTP, secure storage, провайдеры Riverpod, маршруты, тема и общие widgets.
- `lib/features/auth/{domain,data,presentation}`: challenge, OTP, восстановление и выход.
- `lib/features/profile/{domain,data,presentation}`: реальные остатки по клубам,
  выбор языка, модель будущей истории операций.
- `lib/features/qr/{domain,data,presentation}`: проверка QR, пакеты, своя сумма,
  адаптер камеры и декодер PNG/JPEG на Dart.
- `lib/features/payment/{domain,data,presentation}`: идемпотентная отправка,
  восстановление операции, polling заказа/grant, возврат из браузера.
- `lib/l10n/*.arb`: все подписи приложения RU/UZ; `generated` создаётся `gen-l10n`.

Интерфейс повторяет оформление присланных референсов тёмных настроек iOS:
чёрный фон, группы #1C1C1E, цветные плитки иконок и тонкие разделители.
Основной текст 17 pt, крупный заголовок 34 pt, минимальная строка 52 pt,
радиус групп 26 pt, промежутки между группами 32 pt. На iOS используется
системный SF, в веб-среде предусмотрены системные sans-serif fallback-шрифты.
Главная содержит справку и список клубов с эквивалентами остатка по зонам; профиль — круглый аватар,
язык, переход к игровому времени и выход. Тарифы и способы оплаты представлены группами строк.
Нижняя навигация: главная, центральная QR-кнопка,
профиль. Круглая QR-кнопка 56×56 сразу открывает камеру. Загрузка фото,
ручной ввод и соответствующее окно удалены. При закрытии сканера и просмотре
выбранного ПК камера освобождается.
Отметка «Тестовый режим» размещена под содержимым страницы. Язык выбирается
в Cupertino action sheet; информация о просмотре рабочего ПК открывается
по строке в его карточке. Актуальный вид: [home-ru.png](docs/screenshots/home-ru.png).

## Поведение оплаты и восстановления

QR → существующий `POST /api/checkouts` → внешняя страница Click/Payme →
`/payment/return?invoice_id=...` → проверка заказа **и** grant.
Статус `paid` сам по себе означает «Запускаем сессию»; успех показывается
только при `grant_status=accepted`. Ошибка предлагает повторную проверку.
Polling выполняется каждые 3 секунды, без наложения запросов, до 60 проверок;
после паузы можно продолжить вручную. При возврате приложения на передний
план статус проверяется снова.

Точная операция и `Idempotency-Key` сохраняются до отправки. При потерянном
ответе выполняется чтение `/api/mobile/operations/{key}`. Если сервер ещё не
видел запрос, повторяется **тот же запрос с тем же ключом**. При наличии
invoice/grant читается только его статус. После terminal-состояния текущая
операция очищается; ручная повторная проверка продолжает читать тот же ресурс.

`MOBILE_RETURN_BASE_URL` — фиксированный origin мобильного frontend, например
`http://localhost:7357` локально. Пользовательский `return_url` API не принимает.
Маршруты используют обычные URL без hash. Web-хостинг должен отдавать
`index.html` для `/payment/return`, `/qr/*`, `/home` и остальных Flutter-маршрутов.

## Ограничения первого этапа

- Реальные Telegram/Click/Payme и физический Controller → Agent не проверены
  end-to-end в этой рабочей среде. Подтверждены обработчики с изолированной
  PostgreSQL, mock Telegram и существующим mock Core, а также UI с fixtures.
- Камера вынесена в `ScannerView`; выбран `mobile_scanner`. Сканирование
  требует разрешения камеры; при отказе предлагаются настройка доступа и
  повторная попытка. Входящие QR-ссылки по-прежнему открываются через маршруты.
- `flutter_secure_storage` на Web использует браузерное хранилище/WebCrypto,
  а не iOS Keychain; требует HTTPS или localhost. Подробнее:
  [официальная документация](https://pub.dev/packages/flutter_secure_storage).
- При падении backend между резервированием операции и созданием ресурса
  резервирование остаётся `pending`. Автоматическое создание нового платежа
  запрещено; требуется проверка операции оператором. Если ресурс создан,
  invoice/grant сохраняется атомарно вместе с ним и доступен для восстановления.
- Refresh имеет строгую защиту от повторного использования. В одном экземпляре
  клиента обновление объединяется в один запрос. Одновременная ротация одной
  сессии из нескольких вкладок может потребовать повторного входа.
- ARB локализует интерфейс; названия клубов, ПК, зон и тарифов поступают из backend.
- Названия, launch assets и signing исходного iOS scaffold требуют финальной
  настройки перед релизом; iOS сборка и App Store подготовка не выполнялись.
