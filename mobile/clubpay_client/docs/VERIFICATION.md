## Что проверено через UI Chrome

Повторная ручная проверка первого входа: поднят отдельный локальный OTP harness
(`mobiledev`, схема `mobile_browser_sandbox`) и debug Flutter с
`LOCAL_OTP_TEST_MODE=true`. Через UI Chrome подтверждены получение случайного
кода, ошибка неверного кода, успешный вход, пустой баланс в профиле,
восстановление авторизации после reload, выход и требование нового входа
после следующего reload. Telegram contact/delivery в этой проверке имитируются;
HTTP, PostgreSQL, выдача/отзыв токенов и браузерное хранилище работают реально.
Сценарий и команды: [FIRST_LOGIN_TEST.md](FIRST_LOGIN_TEST.md).

После добавления стенда: `flutter analyze` — без замечаний; все **21** тест
прошли в Chrome с `LOCAL_OTP_TEST_MODE=true` и loopback `API_BASE_URL`.
Отдельно проверено, что без флага модель игнорирует тестовый код.
`go test -race -tags mobiledev ./internal/httpapi` с тестовой PostgreSQL прошёл,
включая запрет удалённой/рабочей БД для harness. Прямые HTTP-проверки подтвердили
отклонение повторного OTP, отзыв access после logout и запрет чужого Origin.

До настройки этого harness первый проход проверял только экран входа и ошибку
отсутствующей конфигурации Telegram — перечислено ниже для точности отчёта.

## Что проверено автоматическими тестами в Chrome и Flutter VM

- Нормализация телефона, отсутствие запроса профиля без токенов.
- Атомарная запись пары токенов и стабильный device ID, отзыв новой пары при
  ошибке записи, обработка rejected refresh, объединение параллельных refresh.
- Разбор обычных и Telegram `startapp` QR-ссылок; HTTP остаётся на API origin.
- Декодирование PNG с QR на Dart без нативного scanner.
- `paid + pending` не считается начавшейся сессией; accepted/failed/ended/refunded.
- Потерянный ответ checkout не создаёт новую операцию; восстановление с тем же ключом.
- Пустые и заполненные остатки разных клубов в RU/UZ, сохранение точных секунд.
- Вход на ширине 390 px с увеличенным текстом без overflow.
- Полный widget flow: phone → OTP → реальный для теста ответ профиля → пустое
  время → ручной QR → пакет → checkout → pending grant → accepted.

Widget flow использует типизированные fixtures в Dio interceptor; unit-тесты HTTP
используют adapter. Это проверки клиентского поведения, а не реального Telegram
и не фактическое списание средств у Click/Payme.

## Что проверено на PostgreSQL

- Повторное применение всех миграций.
- Недопустимые номера, неверное устройство, чужой/пустой contact.user_id,
  несовпадение телефона, одноразовость OTP, TTL, 5 попыток, rate limit.
- Вход в существующий `players`, отсутствие выдуманного баланса, хэширование токенов.
- Ротация и отзыв старого access, отзыв семьи при reuse refresh, logout.
- Чужой мобильный игрок не читает заказ, grant или результат операции.
- Checkout требует idempotency key; replay возвращает тот же invoice;
  изменение тела с прежним ключом отклоняется.
- Старый QR token не является mobile access; bearer нельзя протащить через
  legacy `player_auth_token` body в обход идемпотентности.
- Существующий payment callback добавляет сохранённые 725 секунд к покупке.
- Cloud создаёт pending grant, существующий Controller reconciliation подтверждает запуск.
- Существующий finishGrant возвращает 321 секунду в клубной баланс.
- Mobile redeem списывает эти секунды один раз, повтор возвращает тот же grant;
  Controller запускает сессию после pending.
- Audit trail сохраняет события мобильной авторизации.

## Исправление проверки рабочего QR в локальном OTP-стенде

Реальная ссылка пользователя разбиралась правильно, но lookup выполнялся
в изолированной тестовой БД и возвращал 404. Дополнительно при диагностике
рабочая QR-страница и API отдавали nginx 502 Bad Gateway. Свежесть/наличие
этого QR на рабочем сервере при таком ответе проверить невозможно.

В tagged development harness добавлен fallback: только GET публичного QR
на фиксированном api-clubpay.justix.uz, без cookies и local access token,
без redirects, с timeout и фильтрацией полей ответа. Local QR остаются локальными.
Карточки рабочего каталога помечаются preview-only; оплата и тестовый баланс
в них не показываются. Production API от этой ветки кода не меняется.
Ошибка 502 превращается в qr_catalog_unavailable, а 404 остаётся отсутствием
QR. Добавлена повторная проверка сохранённого QR без нового сканирования.

Go-тесты проверяют local hit, remote 200/404/502, отсутствие передачи секретов
и маркировку preview. Flutter-тесты проверяют реальный формат ссылки,
отсутствие auth header у публичного lookup, недоступность платежей/локального
баланса в preview и повтор того же запроса при недоступности каталога.

После исправления: flutter analyze без замечаний; 27 тестов в Chrome прошли;
go test -race -tags mobiledev ./internal/httpapi с PostgreSQL прошёл.
При первоначальной проверке в Chrome точная ссылка пользователя показывала
недоступность рабочего каталога и кнопку повторной проверки: API отвечал 502.
