# Mobile Profile API

## Новые endpoints

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/mobile/auth/challenge` | `{phone:"+998…",device_id:"…"}` → challenge, Telegram link, expires_at |
| `POST /api/mobile/auth/verify` | `{challenge,device_id,otp}` → access/refresh и сроки действия |
| `POST /api/mobile/auth/refresh` | `{refresh_token,device_id}` → новая пара токенов |
| `POST /api/mobile/auth/logout` | `{refresh_token,device_id}` → отзыв сессии, 204 |
| `GET /api/mobile/me` | id, phone, first_name текущего игрока |
| `GET /api/mobile/balances` | `{balances:[{club_id,club_name,balance_uzs,seconds_balance}]}`; пустой массив при отсутствии остатков |
| `GET /api/mobile/orders/{invoice_id}` | Только свой заказ: status, grant_status, pc_label, duration_seconds, session_seconds, checkout_url, grant_id, planned_ends_at |
| `GET /api/mobile/sessions/{grant_id}` | Только собственный grant; статус и длительность без Controller/Agent credentials |
| `GET /api/mobile/operations/{key}` | Результат идемпотентной операции, invoice_id/grant_id, http_status/response |

Profile endpoints требуют `Authorization: Bearer mob_a_…`.
QR-scoped `auth_…` не принимается за мобильную сессию.
Авторизация и профили отвечают с `Cache-Control: no-store`.

## Переиспользованные endpoints и механизмы

- `GET /api/qr/{token}` — текущие ПК, зона, тарифы и доступность провайдеров;
  публичный ответ не содержит внутренних ключей. Flutter распознаёт также
  существующий вариант QR `https://t.me/<bot>?startapp=<token>`.
- `POST /api/checkouts` и `POST /api/player-balance/redeem` теперь дополнительно
  принимают mobile bearer + `Idempotency-Key`. Web-запросы без mobile bearer
  продолжают прежний flow. Mobile token нельзя передать только через legacy body,
  обходя middleware идемпотентности.
- `players`, `player_club_balances`, `player_time_ledger` остаются источниками данных.
  `recordPlayerTime`, автоматическое добавление времени при оплате,
  `finishGrant`, возврат секунд, `refundPlayerBalance` не заменены новым кошельком.
- Существующие checkout, callback, `applyPaymentSuccess`, game_access_grants и
  Controller reconciliation продолжают выполнять платежи и запуск.
  Запуск новой сессии через mobile redeem в Cloud оставляет grant для Controller sync,
  как checkout, вместо прямого обращения к LAN Agent. Проверка срока и типа QR
  для mobile redeem выполняется и при отправке, а не только на экране сканера.
- Старая `/api/player-auth/*` Telegram/QR авторизация сохранена.
- Для Payme/Click возврат мобильного заказа хранится отдельно; возвраты web-заказов
  остаются на `FRONTEND_BASE_URL`.

## Безопасность и миграция

`migrations/011_mobile_profiles.sql` добавляет:

- `mobile_auth_challenges`: отдельный challenge с номером, хэшем device_id,
  Telegram contact binding, OTP digest, попытками и TTL;
- `mobile_sessions`: семейство токенов устройства, абсолютный срок и отзыв;
- `mobile_tokens`: хэши access/refresh, срок, метка использования;
- `mobile_rate_limits`: атомарные счётчики PostgreSQL;
- `mobile_operations`: уникальный `(player_id,request_key)`, хэш тела операции,
  сохранённый ответ и привязка к ресурсу;
- `payment_orders.client_return_url`: фиксированный адрес возврата клиента.

Access: 15 минут. Refresh/session: 30 дней абсолютного срока, без бесконечного
продления. Успешный refresh отмечает предыдущие токены использованными и
создаёт новую пару в одной транзакции; повтор старого refresh отзывает всю
сессию. Logout отзывает её даже при истёкшем access token.

Challenge: 5 минут. OTP: до 3 минут, не дольше challenge, максимум 5 попыток.
Номер — строго +998 и 9 цифр. Device ID — 32–128 символов, приложение создаёт UUID.
Контакт принимается только в личном чате, если `contact.user_id == from.id == chat.id`
и номер совпадает с challenge. Привязка телефона к другой установленной Telegram
идентичности автоматически не переносится; заблокированный игрок не активируется.

Access/refresh/challenge/device хэшируются SHA-256. OTP хранится как HMAC-SHA256
с pepper из Telegram bot secret и хэшем challenge. Секреты/OTP не пишутся в audit
или ошибки. Смена bot token делает незавершённые OTP недействительными.

Лимиты за 15 минут: 3 challenge на телефон, 5 на устройство, 30 на непосредственный
IP соединения; 30 verify-запросов на устройство, 120 на IP плюс 5 попыток каждого challenge.
`X-Forwarded-For` не используется как доверенный IP. За reverse proxy IP-лимит
применится к proxy; для большого трафика нужен доверенный ingress rate limit с
корректной обработкой адресов. Телефонный и device-лимиты независимы от proxy.

Audit пишет события создания challenge, подтверждения контакта, отказа OTP,
входа, refresh, обнаруженного reuse и выхода в существующую `audit_logs`.

Перед production эксплуатацией настройте retention для истёкших challenge,
rate-limit buckets и токенов отозванных/истёкших сессий. Использованные refresh
нельзя удалять до конца жизни сессии: они нужны для обнаружения replay.
Операции нельзя удалять, пока клиент может повторить их ключ; при архивировании
сохраняйте уникальный ключ и ссылки на invoice/grant.

## Остаток клуба и пересчёт зон

`GET /api/mobile/balances` возвращает клубы, в которых у игрока есть остаток,
заказ или игровая сессия. Для каждого клуба: `club_id`, `club_name`,
`balance_uzs` (игровой баланс в сумах), `seconds_balance` (совместимая проекция в базовой цене),
`updated_at`, `controller_synced_at`, `club_online` и `zones`:

```json
{"id":"zone-id","name":"VIP","hourly_price_tiyin":3000000,"seconds_available":1800}
```

В Flutter на главной показывается один игровой баланс клуба в сумах. После
сканирования QR приложение показывает, на сколько времени его хватит для
выбранного ПК. Эквиваленты `zones` — альтернативы одного остатка, их нельзя
складывать. Между разными клубами баланс не переносится.

Миграция `012_zone_time_value.sql` добавляет целочисленные единицы стоимости
`time_value_units = seconds × hourly_price_tiyin`. Это внутренняя оценка
игрового времени, не денежный кошелёк. Доступные секунды целевой зоны:
`floor(time_value_units / target_hourly_price_tiyin)`. Списывается стоимость
только выданных секунд; дробная часть остаётся в клубном остатке.

Цена фиксируется в `game_access_grants.time_value_rate`. Остаток завершённой
сессии оценивается по этой цене; редактирование зоны не переоценивает прошлую
игру. Продление использует сохранённую цену родительской сессии. Пропорция
переноса основана на часовой цене зоны, а не на пересчёте скидки каждого пакета.

Списание и журнал обновляются в одной транзакции с блокировкой баланса.
Повторный ключ события не меняет остаток. При подтверждённой ошибке запуска
возвращается ровно записанный `time_value_delta`; неопределённый запуск
остаётся pending в существующем процессе восстановления. Автоматическое
применение остатка при покупке также выполняет пересчёт.

Кэш Flutter разделён по пользователю и API origin. При сетевой/серверной
ошибке показывается последний непустой ответ с признаком stale; ошибка
авторизации не открывает кэш, а отсутствие кэша не превращается в ноль.
Остатки обновляются каждые 20 секунд и после возвращения приложения.
Для cloud `club_online` требует успешного снимка контроллера за последние
45 секунд. При stale/offline кнопка использования остатка отключена.

### Обновление существующей установки

Нужно совместно обновить Cloud и Controller: новые снимки содержат стоимость,
зафиксированные цены сессий и изменения стоимости в журнале. Старый снимок
без единиц стоимости не перезаписывает уже оценённый баланс; более старые
снимки отсекаются по `updated_at`. Это защита от устаревшего снимка, а не
распределённая блокировка между независимыми базами. Одновременные офлайн-
списания на независимых контроллерах не проверены и не должны включаться
как поддерживаемый сценарий до отдельной проверки протокола синхронизации.

У старых секунд нет надёжной исторической цены зоны. Миграция сохраняет их
как секунды в минимальной текущей цене клуба; исходный `seconds_balance`
остаётся совместимой проекцией. Перед переносом рабочих остатков нужно
сверить это правило с данными клуба, особенно если ранее смешивались VIP
и Standard. Историческую цену нельзя достоверно восстановить из одного числа.

Новая логика проверена на изолированной PostgreSQL и локальном Flutter.
Production-миграция и обновление физических контроллеров в этой задаче
не выполнялись; локальный OTP не даёт доступа к рабочему профилю.
